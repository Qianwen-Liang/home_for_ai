## 一、文档摘要

| 条目 | 内容 |
|---|---|
| **背景** | agent1 多智能体系统已具备基础工具链（~20 个核心工具、6 个 Specialist），但进化机制以被动响应为主，缺乏自主感知、自动反馈闭环和持续优化能力 |
| **目标** | 从六大维度系统性地提升 agent1 的自主进化能力，使系统逐步从"工具调用者"迈向"自主实体" |
| **核心策略** | 以**环境感知**为突破口（学术界共识的关键分水岭、开源界空白），兼顾反馈闭环的自动化改进，渐进式推进多 Agent 协作和元治理 |
| **总工期** | 约 10 周（分三阶段），总计 ~1,500 行新增代码 |

## 二、调研基础

### 2.1 学术文献关键启示

| 来源 | 核心思想 | 对应维度 |
|---|---|---|
| **Reflexion** (Shinn et al., 2023) | Agent 通过语言化反思失败经验，维护情节记忆避免重复错误 | 经验沉淀 |
| **Self-Refine** (Madaan et al., 2023) | 迭代式自我反馈：生成→自评→改进，无需外部监督 | 反馈闭环 |
| **DSPy** (Stanford, 2023) | 将 LLM 调用视为可编程模块，自动优化 prompt | 反馈闭环 |
| **TextGrad** (2024) | "文本梯度"自动优化 LLM 输出，微分思想迁移到文本域 | 反馈闭环 |
| **Agentic AI 综述** (arXiv:2510.25445) | 环境感知是 Agent 从"工具调用者"进化为"自主实体"的关键分水岭 | 环境感知 |

### 2.2 开源框架关键启示

| 框架 | 组织模式 | 可借鉴设计 | 对应维度 |
|---|---|---|---|
| **AutoGen** (Microsoft) | 对话式——Agent 间自由对话协商 | 双向对话协议 | 多Agent协作 |
| **CrewAI** | 角色式——定义角色→分配任务→顺序/层级执行 | 动态角色重组 | 多Agent协作 |
| **LangGraph** | 图式——状态图定义工作流，支持条件分支和循环 | 图执行引擎、条件分支 | 多Agent协作 |
| **MetaGPT** | 公司式——模拟软件公司 SOP | **共享消息池 + SOP 编码** | 多Agent协作 |

### 2.3 关键发现：环境感知是差异化机会

> 目前没有任何主流框架（AutoGen / CrewAI / LangGraph / MetaGPT）原生支持"环境感知"能力。这意味着这是我们建立差异化优势的战略机会。

## 三、任务分解

### 阶段一：基础设施速赢（第 1-2 周）

> 目标：搭建环境感知和反馈闭环的基础设施，产生立即可见的改进效果。

---

#### 任务 A1：系统健康仪表盘

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-A1 |
| **维度** | 环境感知 — 子层 A（系统自感知） |
| **优先级** | 🔴 P0 |
| **预计工时** | 3h |
| **新增文件** | `evolver/health_dashboard.py`（~150 行） |
| **依赖** | 无 |

**现状**：`self_check`、`monitor`、`safety_net` 各自独立运行，数据分散，无统一视图。

**目标**：聚合三个数据源，输出结构化健康报告。每次 Evolver 会话启动时自动运行。

**实现要点**：
```
HealthDashboard
├── HealthStatus enum (HEALTHY / DEGRADED / UNSTABLE / CRITICAL)
├── aggregate() → 调用 self_check + monitor.summary + safety_net.status
├── score() → 综合评分 0-100
├── alert() → 评分 < 阈值时主动告警
└── report() → Markdown 格式报告
```

**验收标准**：
- [ ] 单次聚合耗时 < 200ms
- [ ] 评分规则合理（4 级状态与人工判断一致率 > 80%）
- [ ] 报告含：模块状态矩阵、工具调用 Top-5、异常事件列表、综合评分

---

#### 任务 A2：安全部署流水线

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-A2 |
| **维度** | 反馈闭环 |
| **优先级** | 🔴 P0 |
| **预计工时** | 2h |
| **新增文件** | `evolver/safe_deploy.py`（~100 行） |
| **依赖** | 无 |

**现状**：Evolver 修改代码后需人工运行测试验证，无自动回滚。

**目标**：每次修改后自动运行受影响测试，失败则自动回滚。

**实现要点**：
```
SafeDeploy
├── pre_check() → 记录当前 git hash
├── affected_tests(modified_files) → grep 匹配相关测试
├── run_tests(test_list) → 调用 test_runner.run_single
├── rollback(original_hash) → git checkout 原文件
└── deploy_report() → 成功/失败/回滚状态报告
```

**验收标准**：
- [ ] 修改 1 个 `.py` 文件后能自动定位 ≥ 1 个关联测试
- [ ] 测试失败后 1 秒内完成回滚
- [ ] 回滚后文件内容与修改前完全一致（`git diff` 为空）

#### 任务 A3：使用模式分析器

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-A3 |
| **维度** | 环境感知 — 子层 B（行为环境） |
| **优先级** | 🟡 P1 |
| **预计工时** | 2.5h |
| **新增文件** | `evolver/usage_analyzer.py`（~150 行） |
| **依赖** | 需 `monitor` 积累 ≥ 7 天数据 |

**现状**：`monitor` 记录了工具调用频次和耗时，但数据未被分析利用。

**目标**：定期挖掘使用数据，自动识别热点模块（应优化）和冷门模块（可淘汰或合并），生成"系统瘦身建议"。

**实现要点**：
```
UsageAnalyzer
├── load_data(days) → 从 monitor 加载历史数据
├── hot_spot_analysis() → 识别 Top-N 热点工具
├── cold_spot_analysis() → 识别低频/零调用工具
├── trend_analysis() → 检测调用频次上升/下降趋势
├── bottleneck_detection() → 识别慢工具 + 超时模式
└── optimization_advice() → 生成优化建议报告
```

**验收标准**：
- [ ] 能从 7 天数据中识别 Top-5 热点和 Bottom-5 冷门工具
- [ ] 趋势检测准确率 > 70%
- [ ] 报告含可执行建议（如"合并 X 和 Y 工具"、"为 Z 增加缓存"）

### 阶段二：环境感知深化（第 3-6 周）

> 目标：建立外部技术生态感知能力，完成环境感知三维体系的搭建。

---

#### 任务 B1：技术雷达扫描器

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-B1 |
| **维度** | 环境感知 — 子层 C（技术生态） |
| **优先级** | 🔴 P0 |
| **预计工时** | 4h |
| **新增文件** | `evolver/tech_radar.py`（~200 行） |
| **依赖** | 需联网搜索能力 |

**现状**：系统完全不感知外部技术生态，所有外部信息依赖人类提供。

**目标**：建立定期技术雷达扫描机制，每周自动搜索 Python 生态关键动态，生成"技术雷达简报"。

**扫描范围**：
| 类别 | 扫描对象 | 频次 |
|---|---|---|
| 安全 | Python 安全公告、关键依赖 CVE | 每周 |
| 框架 | LangChain / AutoGen / CrewAI / LangGraph 新版本 | 每两周 |
| 工具链 | pytest / mypy / ruff 等开发工具新版本 | 每月 |
| 趋势 | Hacker News / Reddit r/MachineLearning / arXiv 热门论文 | 每周 |

**实现要点**：
```
TechRadar
├── RadarCategory enum (SECURITY / FRAMEWORK / TOOLCHAIN / TREND)
├── scan(category) → 执行搜索，解析结果
├── compare_versions() → 对比当前版本与最新版本
├── assess_impact() → 评估对 agent1 的影响等级 (CRITICAL/HIGH/MEDIUM/LOW)
├── generate_briefing() → 生成结构化简报
└── archive() → 归档到 memory/tech_radar/
```

**验收标准**：
- [ ] 首次扫描覆盖 4 个类别、≥ 10 个数据源
- [ ] 简报含：标题、摘要、影响评估、建议行动、来源链接
- [ ] 简报归档可检索（存入 `knowledge` 系统）

#### 任务 B2：环境感知统一入口

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-B2 |
| **维度** | 环境感知（整合 A + B + C 三个子层） |
| **优先级** | 🟡 P1 |
| **预计工时** | 3h |
| **新增文件** | `evolver/env_awareness.py`（~120 行） |
| **依赖** | E-A1, E-A3, E-B1 |

**现状**：三个子层的感知各自独立，无统一调度。

**目标**：提供统一的环境感知调度器，管理扫描周期、聚合报告、触发告警。

**实现要点**：
```
EnvironmentAwareness (单例)
├── layers = {SELF, BEHAVIORAL, ECOLOGICAL}
├── schedule() → 管理各层扫描周期
├── pulse() → 执行一轮全层扫描
├── aggregate_report() → 三层结果合并为统一环境报告
├── detect_anomalies() → 跨层异常关联检测
└── advise() → 基于环境状态给 Evolver 提供进化建议
```

**验收标准**：
- [ ] `pulse()` 能在 5 秒内完成三层扫描
- [ ] 统一报告含三层摘要 + 交叉关联分析
- [ ] 异常关联检测至少覆盖 2 种跨层模式（如"外部安全漏洞 + 内部受影响模块"）

### 阶段三：深度进化（第 7-10 周）

> 目标：推进多 Agent 协作改进和元治理能力，形成进化机制的自我进化。

---

#### 任务 C1：共享黑板工作内存

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-C1 |
| **维度** | 多 Agent 协作 |
| **优先级** | 🟡 P2 |
| **预计工时** | 5h |
| **新增文件** | `memory/blackboard/__init__.py` + `blackboard_manager.py`（~200 行） |
| **架构变更** | 是 — 新增共享内存目录 |
| **依赖** | 需协调所有 Agent |

**现状**：Agent 之间通过 JSON 字符串单向传递结果，无共享工作区。

**目标**：借鉴 MetaGPT 的"共享消息池"，建立所有 Agent 可读写的中间产物空间。

**实现要点**：
```
Blackboard
├── BoardItem (id, type, content, author, timestamp, status)
├── post(item) → 发布到黑板
├── read(item_id | type_filter | author_filter) → 读取
├── subscribe(pattern) → 订阅感兴趣的内容（发布时自动通知）
├── revise(item_id, new_content) → 修订（保留修订历史）
├── finalize(item_id) → 标记为最终版本
└── cleanup(ttl) → 清理过期条目
```

**验收标准**：
- [ ] 至少 2 个不同类型的 Specialist 能读写同一黑板条目
- [ ] 修订历史完整保留（≥ 3 次修订可追溯）
- [ ] 并发写入无竞态（文件锁机制）

---

#### 任务 C2：进化策略引擎

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-C2 |
| **维度** | 元治理 |
| **优先级** | 🟢 P2 |
| **预计工时** | 4h |
| **新增文件** | `evolver/evolution_strategy.py`（~180 行） |
| **依赖** | E-A1（健康仪表盘） |

**现状**：进化机制硬编码在 Evolver 的系统提示词中，无法根据场景调整。

**目标**：实现可切换的进化策略，根据系统健康状态自动推荐或切换策略模式。

**三种策略模式**：
| 模式 | 特征 | 适用场景 |
|---|---|---|
| **激进** (AGGRESSIVE) | 快速迭代，容错率高，自动执行 | 早期探索、实验性功能 |
| **保守** (CONSERVATIVE) | 每次改动需多重验证，人工审批 | 核心模块修改、生产环境 |
| **维护** (MAINTENANCE) | 仅修复 Bug，不做功能增强 | 稳定期、冻结期 |

**实现要点**：
```
EvolutionStrategy
├── StrategyMode enum (AGGRESSIVE / CONSERVATIVE / MAINTENANCE)
├── current → 当前模式
├── recommend(health_score) → 基于健康评分推荐模式
├── switch(mode) → 切换模式（记录切换原因和时间）
├── guardrails() → 当前模式下的行为约束规则
└── history() → 模式切换历史
```

**验收标准**：
- [ ] 三种模式可手动切换，切换后行为约束生效
- [ ] 自动推荐准确率 > 70%（基于健康评分的模式推荐与人工判断一致）
- [ ] 模式切换历史完整可审计

---

#### 任务 C3：进化审计日志

| 属性 | 内容 |
|---|---|
| **任务 ID** | E-C3 |
| **维度** | 元治理 |
| **优先级** | 🟢 P2 |
| **预计工时** | 2h |
| **新增文件** | `evolver/audit_log.py`（~100 行） |
| **依赖** | E-C2 |

**现状**：无系统化的进化决策记录，事后难以追溯"为什么做了这个决定"。

**目标**：记录每次进化决策的完整上下文，形成可审计的进化历史。

**实现要点**：
```
AuditLog
├── AuditEntry (timestamp, decision, rationale, expected_effect,
│               actual_effect, files_changed, rollback_hash, strategy_mode)
├── log(entry) → 追加审计条目
├── query(start, end, tag) → 按条件查询
├── report(entry_id) → 单条详细报告
└── stats() → 统计（总决策数、成功率、回滚率等）
```

**验收标准**：
- [ ] 每次 Evolver 修改操作自动记录审计条目
- [ ] 支持按时间范围和标签查询
- [ ] 审计日志持久化到 `memory/audit/`

## 六、风险评估

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| **联网扫描被限制** | 中 | E-B1 无法执行外部搜索 | 提供离线备选方案：人工输入关键动态后由系统分析 |
| **黑板并发写入竞态** | 低 | 数据损坏 | 使用文件锁（`fcntl.flock`），单写入者模式 |
| **健康评分规则不准确** | 中 | 误告警或漏告警 | 初期以人工校准为主，积累数据后调整阈值 |
| **测试覆盖不足导致回滚误判** | 中 | 安全部署流水线可靠性下降 | 每次修改后至少运行 2 个相关测试；逐步提升测试覆盖率 |
| **阶段间依赖阻塞** | 低 | 后续阶段无法启动 | 各任务设计为松耦合，可独立开发和测试 |
