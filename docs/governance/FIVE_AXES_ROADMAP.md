# 全项目五维升级规划书

> 版本：v1.0 ｜ 制定日期：2026-10-30 ｜ 对应任务：T2800
> 前置资产：G1-G5 门禁、CI、分支保护、102 个僵尸脚本归档（2026-10-30 完成）

---

## 一、这份文档的定位

**它不是一个目标清单，而是一组可执行的断言。**

过去本项目多次出现"形容词驱动"的治理：目标写着"提升鲁棒性/性能"，于是每次治理都产出一批一次性验证脚本，用完即弃，缺陷反复复发（测试污染知识库清理过两次仍复发；K1/K2 在基线里悬空三个月）。

因此本文档的硬约束：

| 原则 | 含义 |
|---|---|
| **每个"高"必须落到断言** | 无法写成"违反时哪个命令会变红"的条目，一律不收 |
| **每个断言必须有基线** | 先测量，再定阈值；不接受拍脑袋数字 |
| **治理配额上限 30%** | 治理不是目的。超过 30% 的精力投入基建即视为失衡，须转回主线 |
| **每阶段可独立回滚** | 阶段间无强耦合，任一段失败不影响其他段 |

## 三、五维定义与断言

每个维度给出：**定义 → 现状 → 断言 → 度量方式**。
断言编号用于门禁映射，`[已有]` 表示已被现有门禁覆盖，`[待建]` 表示需新增。

### 3.1 维度①鲁棒性

**定义**：系统在异常输入、依赖缺失、并发竞争、外部故障下，仍给出**确定且可诊断**的结果。

| 编号 | 断言 | 现状 |
|---|---|---|
| R1 | 任意注册工具对 6 类边界输入（缺失/类型错/越界/空值/超长/特殊字符）不得泄漏未包装异常 | `[已有]` 契约 C4 |
| R2 | 任意失败返回必须携带机器可判定标记，禁止静默失败 | `[已有]` G2 |
| R3 | 并发写入不得丢数据，ID 必须唯一 | `[已有]` G2 |
| R4 | 多智能体流水线在任一节点失败时，必须回滚且不残留脏状态 | `[待建]` |
| R5 | 进程中断后，checkpoint 必须能恢复到一致状态 | `[待建]` |

**主要缺口**：R4、R5。当前契约只覆盖"工具级"，而 orchestrator / village / task_dispatcher 这些**协同级**组件完全没有契约守护——这是最大的鲁棒性盲区。

### 3.2 维度②性能

**定义**：核心路径延迟可预测，长尾不失控，退化能被自动捕获。

| 编号 | 断言 | 现状 |
|---|---|---|
| P1 | knowledge 关键词检索 p50 < 0.15s，退化 >20% 即红 | `[已有]` G4 |
| P2 | monitor 必须记录 p50/p95，而非仅均值 | `[待建]` |
| P3 | run_command p95 < 60s，单次最长 < 120s | `[待建]` |
| P4 | safe_deploy 全流程 < 10s | `[待建]` |

**为什么 P2 优先**：当前 monitor 只有均值 3,495.6ms，而历史上 `safe_deploy` 单次 33s、`run_command` 最长 115s——**这些长尾被均值完全掩盖**。没有分位数，性能治理就是盲的。

### 3.3 维度③效率

**定义**：单位任务完成的资源消耗（token、调用次数、墙钟）可控且可优化。

| 编号 | 断言 | 现状 |
|---|---|---|
| E1 | 工具 schema 总 token ≤ 3,500（防回弹） | `[已有]` 需纳入门禁 |
| E2 | 单任务工具调用次数中位数 ≤ 基线值 | `[待建]` 需先测基线 |
| E3 | 超上下文预算时必走裁剪路径，不得整段灌入 | `[已有]` budget 模块 |

**关键认识**：效率不是"更快"，而是"不做无用的工作"。本项目最大的效率损耗不是单次调用慢，而是**同一诊断被反复执行**（80+ 个一次性脚本曾各做一遍同样的验证）。

### 3.4 维度④标准化

**定义**：接口、错误、数据、流程有统一契约，并由门禁强制。

| 编号 | 断言 | 现状 |
|---|---|---|
| S1 | 16 个注册工具 100% 通过 MCP 对齐的 C1-C6 | `[已有]` 契约测试网 |
| S2 | 所有错误必须归入三层契约（RETRYABLE/FATAL/REJECTED） | `[已有]` errors.py |
| S3 | 每个 `tools/` 模块必须提供 `TOOL_DEFINITION`，或显式标注"非工具" | `[待建]` |
| S4 | 新增工具必须同时具备：定义 + 契约断言 + 回归测试，否则门禁红 | `[待建]` |
| S5 | 幽灵条目清零（映射表中的名字必须有对应实现） | `[待建]` |

**主要缺口**：S3-S5。16 个注册工具有契约，但 **24 个 internal_subsystem 完全没有**——它们占代码量的大头，却处于"有代码、无守护"状态。

### 3.5 维度⑤结构化

**定义**：每个模块处于"注册 / 归档"明确二态，无中间态；依赖方向清晰无环。

| 编号 | 断言 | 现状 |
|---|---|---|
| T1 | 每个模块必须是 registered 或 archived，不得存在 unresolved | `[待建]` 现有 2 个幽灵 |
| T2 | 模块依赖图必须无环 | `[待建]` |
| T3 | 依赖方向单向：core → tools → evolver，禁止反向 | `[待建]` |
| T4 | 单文件 ≤ 1,500 行 | `[待建]` 现 3 个文件接近上限 |

**T4 的现状风险**：

| 文件 | 行数 | 状态 |
|---|---|---|
| specialist_base.py | 1,491 | 逼近上限 |
| repair_executors.py | 1,411 | 逼近上限 |
| knowledge_store.py | 1,391 | 逼近上限 |

这不是硬性美观问题——**超大文件的真实代价是修改时的回归风险**，而回归风险正是我们刚花大力气用门禁去接住的东西。从源头降低单点复杂度，比事后加检查更划算。

### P1｜清债（预计 3–5 天，优先级最高）

目标：**把已知遗留清零，让"待办"不再无限堆积**。

| 任务 | 对应断言 | 验收 |
|---|---|---|
| 1. 清理 2 个幽灵条目（blackboard / offline_research） | T1 / S5 | `legacy_tools.json` 中 unresolved = 0 |
| 2. monitor 增加 p50/p95 统计 | P2 | 输出含分位数，且能回溯历史长尾 |

| 5. 评估 24 个 internal_subsystem 去留 | S3 / T1 | 每个给出"保留并补契约"或"归档"结论 |

**为什么 P1 优先于扩展**：现在有一批"已登记但未处理"的项（K3/K4/F1/F2/幽灵条目）。如果先做扩展，这些会变成新的 K1/K2——**我们刚清理掉的那类悬空项**。

---

### P2｜扩面（预计 2–3 周）

目标：**把守护范围从"工具级"扩到"协同级"**。

| 任务 | 对应断言 | 验收 |
|---|---|---|
| 6. 多智能体协同契约（orchestrator / village / task_dispatcher） | R4 | 节点失败时回滚，无脏状态 |
| 7. checkpoint 崩溃恢复验证 | R5 | 强杀进程后能恢复一致状态 |
| 8. 长尾性能治理（safe_deploy 33s → <10s） | P4 | 连续 10 次达标 |
| 9. 新增工具三件套门禁（定义+契约+测试） | S4 | 缺任一项即红 |

**这是本规划中风险最高的阶段**——它触及运行时行为而非静态检查，且多智能体没有现成契约标准可抄。建议每项独立提交、独立回滚。

## 五、验收与失败判据

### 5.1 整体验收（达到即视为五维目标达成）

| 维度 | 达成条件 |
|---|---|
| 鲁棒性 | R1-R5 全部有断言且门禁绿 |
| 性能 | P1-P4 全部有基线且无退化 |
| 效率 | E1-E3 全部有度量 |
| 标准化 | S1-S5 全部满足，unresolved = 0 |
| 结构化 | T1-T4 全部满足，依赖无环无反向 |

### 5.2 失败判据（预注册，防止事后合理化）

**什么证据出现即判定本规划失败：**

1. 任一阶段引入的检查在 7 日内被降级为 `accepted` 而无明确出口条件
2. 门禁自检用例被删除或跳过（意味着失去了"门禁能不能抓贼"的验证）
3. 治理投入连续两周超过总精力 30%，且主线任务无推进
4. 新增断言的阈值来自拍脑袋而非实测基线
5. 出现"登记了但超过 1 个月未处理"的新遗留项

**止损点**：连续 2 个阶段验收不通过，暂停治理，全面回归主线，重新评估方法论。

## 六、与主线任务的关系（最重要的一节）

### 6.1 治理配额

| 项目 | 配额 |
|---|---|
| 治理 / 基建 | **≤ 30%** |
| 业务主线（T2738 SAT 求解器 / T2769 BYOB benchmark） | **≥ 70%** |

**这条配额是硬约束。** 本项目历史上出现过"一直在治理、始终不产出"的倾向——80+ 个一次性脚本就是证据：它们每一个都看起来像在做正事。

### 6.2 主线不受本规划阻塞

本规划的所有任务都是**加法**（增加守护），不改变业务逻辑。因此：

- T2738 SAT 求解器（当前 78%）可以与本规划**并行推进**
- T2769 BYOB benchmark（0%，依赖已就绪）**不应等待**本规划完成

### 6.3 建议的执行节奏

```
P1 清债（3-5天，一次性）
        ↓
   回主线 2-3 周（T2738 / T2769）
        ↓
P2 扩面（挑 2-3 项最高价值的，不追求全做）
        ↓
   长期：主线为主，治理按季度维护
```

**不要试图把 P2 一口气做完。** P2 的 5 项里，只有"多智能体契约"和"长尾治理"有明确价值，其余可按需。

## 七、风险与反模式

| 风险 | 表现 | 缓解 |
|---|---|---|
| **装饰性治理复发** | 新增文档/基线但不接门禁 | 每条断言必须回答"违反时哪个命令变红" |
| **门禁误报消耗信任** | 已发生 2 次（观察者效应、CPU 余热） | 新增门禁必须配红绿双向自检 |
| **阈值拍脑袋** | "提升 20%" 无依据 | 先测基线，再做 2 倍安全边际 |
| **治理挤压主线** | 连续两周 >30% 配额 | 配额硬约束 + 月度回顾 |
| **扩面失控** | P2 全做导致战线过长 | P2 只挑 2-3 项 |
| **过期登记** | accepted 项永不复核 | 每月回顾出口条件是否满足 |

## 九、能力边界（本规划的局限）

1. **多智能体契约无现成标准可抄**——R4/S3 的断言设计需自行摸索，可能需 2-3 轮迭代才能稳定
2. **性能阈值跨环境不可比**——G4 已遇到（跨平台基线失效），P3/P4 会有同样问题，可能需要专用 runner
3. **未评估 24 个 internal_subsystem 的实际使用频率**——"保留并补契约"的成本可能远超预期，需先测量再决策
4. **配额靠自觉执行**——没有机制强制"不超过 30%"，只能靠月度回顾
5. **本规划不涉及业务能力提升**——它只保证"不出错"，不保证"做得对"；后者才是主线任务的目标
