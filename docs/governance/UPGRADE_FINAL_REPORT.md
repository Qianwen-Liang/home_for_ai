## 三、按梯队的工作明细

### 第 1 梯队 · 契约普及

**调研推翻了原计划**。原定"四个基础设施模块普及率都低，都要推广"，实测后有三个是集中式设计：

| 模块 | 表面普及率 | 实测结论 |
|---|---|---|
| `middleware` | 2.4% | **集中式**，已在 agent1 主路径，无需各模块 import |
| `budget` | 9.5% | 唯一事实来源，4 个使用者恰好覆盖所有长文本产出点 |
| `registry` | 19% | 定义源，8 个使用者已够 |
| `errors` | 23.8% | **唯一真缺口，且不是覆盖率问题** |

`errors` 的真问题是接口错配：`classify()` 接收异常对象，而 agent1 把失败包装成 `RuntimeError(result[:120])` → 全部塌缩为 FATAL，"该重试"和"该改参数"的语义完全丢失。

修复：新增 `classify_result()` 从返回文本恢复语义；middleware 复用统一契约（删掉自建的第二套逻辑）；ERROR_MAP 补全 Python 内置异常（36 → 53 种）。

### 第 2 梯队 · 高频基础模块（8 个）

| 模块 | 发现 | 处理 |
|---|---|---|
| `self_check` | 硬编码 10/42 模块，报「🟢 优」但覆盖仅 23% | 自动发现 → 100%，**立刻抓出 2 个缺陷** |
| `specialist_base` | 与 debugger_agent 循环导入 | 修复（连带否证 F1/F2 归因） |
| `role_system` | 命名契约不符 | 改名 + 加通用命名断言 |
| `decision_engine` | 被移出注册表 → 从不被调用 | 恢复注册 + 接入 task_tracker |
| `message_bus` | 实测并发无缺陷 | 只补回归测试 |
| `agent_manager` | 心跳只记不判，崩溃 agent 仍被派活 | 加 TTL，三处接入 |
| `safety_net` | `check()` 从不执行 | `record_and_check` 接入 agent1 |
| `web_search` | 降级已可见，无缺陷 | 只补回归测试 |

**4 个修了代码，2 个只补测试，2 个附带发现（循环导入、flaky 根因）。**

### 第 3 梯队 · 协同系统（4 个）

| 模块 | 缺陷 |
|---|---|
| `task_dispatcher` | 无 Saga 补偿 —— dispatch 中途失败，Agent 永久卡 busy |
| `orchestrator` | 文档承诺"自动重试"，实现只有手动入口 |
| `checkpoint_manager` | 排序依赖 `time_ns()`，Windows 实际分辨率 15.6ms → 50% flaky |
| `offline_runner` | **单轮挖出 4 个缺陷**（见下） |

`offline_runner` 的四个：
1. `task_id` 秒级时间戳冲突 → 同秒提交静默覆盖，任务丢失
2. `cancel` 设 status 为 `paused` 却返回"已取消" → 取消是假的，可被 resume 撤销
3. `execute` 只拦 `running`，`done`/`cancelled` 可重跑 → 结果被覆盖
4. `resume` 设 `running` 而 `execute` 拒 `running` → **pause→resume→execute 永久卡死**

### 第 4 梯队 · 进化系统（4 个）

| 模块 | 缺陷 |
|---|---|
| `health_dashboard` | 用均值判延迟健康 → 长尾被完全掩盖 |
| G4 阈值 | 20% 阈值落在实测噪声带（29.9%）内部 → 随机假警报 |
| `effect_evaluator` | 均值差衡量改进；**评分逻辑又独立算了一遍均值差**（改口径没改判定） |
| `cycle_tracker` | 连续退化检测**可用算术证明不可达** |
| `audit_log` | 94 条记录只写不读 |

`cycle_tracker` 的证明：
```
触发 consecutive 需 a-c ≥ 10
避开 single 需 a-b < 5 且 b-c < 5
但 a-c = (a-b)+(b-c) < 10  ← 矛盾
```
即「连续退化 → 置 PAUSED → 停止自改进」这条保护链**从未生效过**。

## 五、方法论沉淀：七种失效形态

本次修复的 27 个缺陷，绝大多数**不是功能写错了**，而是机制存在但没接上。归纳为七种形态：

| # | 形态 | 典型实例 | 判别方法 |
|---|---|---|---|
| 1 | 资产存在但不被使用 | 知识库只积不用 | 这份数据有消费者吗 |
| 2 | 能力存在但入口不通 | decision_engine 移出注册表 | 调用方能到达它吗 |
| 3 | 状态记录了但不参与判断 | last_heartbeat 只记不判 | 这个字段影响任何分支吗 |
| 4 | 传感器存在但采样器没开 | safety_net record 有、check 无 | 采集之后有人判定吗 |
| 5 | 检测逻辑自相矛盾 | cycle_tracker 不可达检测 | 阈值条件联立有解吗 |
| 6 | 声明 ≠ 实现 | orchestrator 自动重试 | 文档里的每个动词，代码里有对应实现吗 |
| 7 | 报错 ≠ 恢复 | dispatcher 无 Saga 补偿 | 异常后系统其余部分还能正常工作吗 |

### 共享的判据

> **这个机制的输出，会影响任何后续行为吗？**
> 如果答案是否，它就是装饰品。

### 三条可复用的操作原则

**① 阈值必须由实测噪声推出，不能凭直觉。**
G4 的 20% 阈值踩在噪声带（29.9%）内部，随机误报。流程：测噪声带 → 阈值 = 噪声上限 × 安全系数 → **红绿双向验证**。
不做红向验证，就无法区分"修好了"和"调松了"。

**② 基线本身也要抗噪。**
旧的性能基线是单次测量（0.0430），比 12 轮的最小值（0.0504）还低 —— **用噪声样本当基准，等于把噪声固化**。改为 3 轮取中位数，并记录 `noise_band_pct`。

**③ 测试不能锁定被测系统的当前状态。**
本轮两次踩到：
- `fix_actions`（测试基于旧设计）
- `test_pause_resume` 断言 resume 后是 running（**锁定的正是卡死缺陷**）

判别：测试里若出现具体模块名或具体 bug 症状，大概率锁定了过时状态。

## 七、能力边界（本次工作的局限）

1. **外部检索质量不稳定**——多次搜索返回无关结果（如把 `t-digest` 当成字母 t、把 architecture 返回建筑学词典）。真正有价值的外部依据只有少数几个：MCP SEP-1303、go-sundheit、idemkit、Saga 模式。其余结论主要来自本地实证。
2. **性能门禁在共享环境本质不可靠**——G4 已放宽到 50% 并加 CV 自检，但仍是"足够大的退化才抓得住"，细粒度退化无法检测。
3. **多处度量口径仍是近似**——`health_score` 混合了 self_check/monitor/safety_net 三个源，其中 monitor 是累计值，新调用的错误会拉低分数，与"改进"无关。这个归因问题未解决。
4. **未覆盖多智能体协同的运行时一致性**——dispatcher/orchestrator 修的是静态逻辑缺陷，真实并发协同下的状态一致性没有压测过。
5. **`evolver/` 中仍有 13 个模块未逐个审查**（self_improver 1247 行、improvement_generator 1176 行、automated_patcher 895 行等），本次只覆盖了计划内的 4 个。
