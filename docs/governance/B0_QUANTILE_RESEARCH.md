# B0 调研：在线分位数算法与性能基线方法

> 任务：T2818（B0 / T2807 前置）｜日期：2026-10-31
> 结论：选 **DDSketch 风格的相对误差桶**，纯 Python 实现约 80 行，1% 相对误差，固定 ~2.8 KB

---

## 一、问题定义

`tools/monitor.py` 当前每个工具只存 6 个聚合值：

```python
{"calls", "errors", "total_duration", "max_duration", "min_duration", "last_called"}
```

**这导致三个后果**：

1. **无法算分位数**。只有均值，而均值会被长尾完全污染——`run_command` 均值 7,054ms，实际最长 120,375ms，两个数量级差距下均值毫无代表性。
2. **无法回答"慢在哪里"**。P3/P4 断言（run_command p95 < 60s、safe_deploy < 10s）全部依赖分位数。
3. **每次 `record` 都全量写 JSON**。867 次调用 = 867 次磁盘写，这本身是性能负担，且会让"加字段"的代价变高。

## 二、候选算法

| 方案 | 误差保证 | 存储 | 可合并 | 实现复杂度 |
|---|---|---|---|---|
| **全样本** | 精确 | 随样本线性增长 | 是 | 无 |
| **线性桶** | 取决于桶宽与数据范围 | 固定 | 是 | 极低 |
| **P²**（Jain & Chlamtac, CACM 1985） | 单分位数近似，无全局保证 | **5 个标记** | 否 | 低（~80 行） |
| **t-digest**（Dunning） | 极端分位数 ppm 级 | 压缩簇，序列化很小 | 是 | 高（参考实现 <1000 行） |
| **HDR Histogram**（HdrHistogram） | 由有效数字位数控制（3 位≈0.1%） | 固定（按范围与精度） | 是 | 中 |
| **DDSketch**（DataDog） | **相对误差保证**（可设 1%） | 对数桶，固定 | **是（全可合并）** | 低（~80 行） |

### 2.1 一手来源要点

**t-digest**（`tdunning/t-digest` README）：
- 1 维 k-means 变体，簇极紧凑，序列化很小
- 极端分位数 ppm 级精度，中间分位数典型 <1000 ppm
- ~140 ns/add，参考实现 <1000 行

**HDR Histogram**（`HdrHistogram/HdrHistogram` README）：
- 可配置整数范围 + 有效数字精度，3 位有效数字 → 量化误差 ≤ 0.1%
- 固定空间与时间成本，记录 3–6 ns
- 例：0 到 3,600,000,000 范围、3 位精度，可覆盖 1μs 到 1 小时

**DDSketch**（`DataDog/sketches-java` README）：
- **相对误差保证**：设 1%，期望分位数 100 时结果必在 [99, 101]；期望 1000 时必在 [990, 1010]
- **fully mergeable**：多实例 sketch 可合并到中心节点

**P²**（`absmall/p2`，原论文 CACM 1985）：
- 只用 5 个标记估计任意分位数，无需存储观测值
- 局限：单分位数最优，多分位数需多组标记；不可合并

## 三、本地实证（`memory/cmd_output/quantile_bench.py`）

模拟 900 个 `run_command` 延迟样本（70% 快命令 2–50ms，22% 中等 50–2000ms，7% 慢 2–30s，1% 打满超时 110–120s）。

精确值：p50 = 36.63ms，p95 = 16,230.74ms，p99 = 113,099.92ms

| 方案 | p50 误差 | p95 误差 | p99 误差 | JSON 大小 |
|---|---|---|---|---|
| 线性桶(200) | **722.20%** | 1.66% | 0.15% | 663 B |
| DDSketch(1%) | 0.94% | **0.43%** | **0.56%** | 2,835 B |
| DDSketch(5%) | 4.67% | 3.59% | 2.40% | 875 B |
| HDR(3 位有效) | 1.44% | 5.12% | 3.63% | 2,202 B |
| 全样本 | 精确 | 精确 | 精确 | 6,608 B |

### 3.1 关键发现：线性桶彻底失效

**p50 误差 722%**。原因：数据跨 5 个数量级（2ms → 120,000ms），线性桶宽 = max/200 = 600ms，而 p50 只有 36.63ms——**所有快命令都落进第一个桶**。

这是本项目特别容易踩的坑：`run_command` 的延迟分布是极端长尾的，**任何等宽分桶都不可用**。

### 3.2 DDSketch 综合最优

- 1% 相对误差：三次分位数误差均 <1%
- 2,835 B：比全样本省 57%
- **大小与数据范围相关，与样本量无关**——这是它相对全样本的决定性优势

### 3.3 为什么全样本不适合

| 样本量 | 全样本 JSON | DDSketch(1%) |
|---|---|---|
| 900 | 6.6 KB | 2.8 KB |
| 10,000 | ~73 KB | ~2.8 KB |
| 100,000 | ~730 KB | ~2.8 KB |

`run_command` 已有 867 次调用，长期增长到十万级是可预期的。全样本方案会线性膨胀，且**每次 `record` 都要重写整个文件**。

## 四、选型结论

### 采用：DDSketch 风格相对误差桶

理由：

1. **精度可证**：相对误差 1%，不是"大致准"
2. **大小恒定**：与样本量无关，长期稳定
3. **可合并**：将来若要多智能体/多时段聚合，天然支持
4. **实现简单**：核心只是 `ceil(log(v)/log(gamma))` 一个映射，纯 Python ~80 行
5. **零依赖**：实测 `tdigest` / `ddsketch` / `hdrh` **均未安装**，必须自实现；DDSketch 是其中最简的

### 参数选择

```
relative_error = 0.01        # 1%
gamma = (1+ε)/(1-ε) = 1.0202
每倍频程桶数 = 1/log(gamma) ≈ 49
数据范围 2ms ~ 120s（≈5.8 倍频程）
→ 约 285 个桶，实测 JSON 2.8 KB
```

### 数据模型设计

```python
"tools": {
  "run_command": {
    "calls": 867, "errors": 0,
    "p50_ms": 120.5, "p95_ms": 15300.0, "p99_ms": 118000.0,   # 由 sketch 派生
    "sketch": {                                                # DDSketch 状态
      "rel_err": 0.01,
      "buckets": {"-512": 3, "1201": 40, ...},
      "zero": 0, "min": 2.1, "max": 120375.1
    }
  }
}
```

保留 `total_duration`/`max`/`min` 以向后兼容现有调用方。

## 五、同时要解决的两个衍生问题

### 5.1 每次 record 全量写盘

当前 `record()` 末尾直接 `self._save()`。867 次调用 = 867 次写。

**方案**：脏标记 + 延迟落盘（与 knowledge_store 的 `flush_cache` 同一模式）。
- `record()` 只更新内存并置脏
- `summary()` / `report()` / 进程退出时统一 flush

风险：进程被强杀会丢最近数据。用 `atexit` 兜底。

### 5.2 历史数据无法补算分位数

现有 `monitor_data.json` 只有聚合值，**无法反推历史分位数**。

**策略**：不迁移历史。新字段从本次改造后开始积累，并在报告中标注"分位数数据自 2026-10-31 起"。这比伪造历史数据诚实。

## 六、待验证事项（实施前）

1. **桶数量上界**：若出现异常大延迟（如 10 分钟），桶数会线性增加。需要设上限 + 溢出桶
2. **精度回归测试**：DDSketch 的误差必须被测试锁定（用已知分布对比精确分位数）
3. **写盘频率**：延迟落盘后需要验证"进程正常退出不丢数据、异常退出丢最少"
4. **与 G4 的关系**：G4 当前用 knowledge 检索 p50 做基线，B0 之后应扩展到 run_command p95

---

## 七、能力边界

1. 实证数据是**模拟生成**的，非真实 `run_command` 样本（monitor 未存原始样本）。分布参数依据是均值 7054ms、max 120375ms，真实分布可能更偏斜
2. 未实测 DDSketch 在极端值（>10 分钟）下的桶增长
3. 未评估与 Prometheus/OTel 的导出兼容性（本项目零依赖，暂不做导出）
4. P² 算法未做本地实测——它只适合单分位数，与"同时要 p50/p95/p99"的需求不符，已排除
5. t-digest 未实测：精度更好但实现复杂度高（<1000 行 vs 80 行），在本项目规模下性价比不足
