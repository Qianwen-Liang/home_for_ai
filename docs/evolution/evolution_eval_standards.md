# 🧬 Agent 1 进化评估标准 v2.0

> 本文件定义"一次进化改进是否有效"的**严格且多样**判定标准。
> 目的是防止"虚假增益"和"无用功"——只有通过本标准的改进才被记为有效进化。
>
> 配套：`evolution_protocol.md`（循环机制）、`effect_evaluator.py`（实现）、`audit_log.py`（审计）

---

## 一、核心原则

1. **对照实验原则**：评估必须基于"改进前 vs 改进后"的严格时序分离，`before` 快照必须在**改动落地之前**采集。
2. **多维原则**：单一指标（尤其健康分）不构成结论，必须五维综合。
3. **真实性原则**：测试通过率必须**实际运行**测试得到，禁止估算或"默认全过"。
4. **一票否决原则**：正确性/健壮性/功能回归出现退化时，无论其他维度增益多少，一律判为退化。
5. **可追溯原则**：每条决策必须回填 `outcome + actual_effect + 量化分数`，不可只记决策不记结果。

---

## 二、五维评估指标（权重总和 = 1.0）

| 维度 | 权重 | 指标来源 | 是否否决项 |
|:---|:---:|:---|:---:|
| **正确性** Correctness | 0.30 | 测试通过数/失败数（实际运行 test_runner） | ✅ |
| **健康** Health | 0.25 | 健康评分、self_check 通过/失败/警告数 | ❌ |
| **性能** Performance | 0.20 | 关键模块导入耗时（子进程×3取中位数）、平均响应、慢工具数 | ❌ |
| **健壮性** Robustness | 0.15 | 连续错误数、自救激活、错误率 | ✅ |
| **功能回归** Regression | 0.10 | 核心工具 smoke test（实际调用验证不报错） | ✅ |

---

## 三、一票否决项（Veto Rules）

满足**任一**即判定 `degraded`，即使其他维度净增益：

1. **测试失败数增加**：`after.test_failed > before.test_failed`（改进引入了新的测试失败）
2. **新引入连续错误**：`before.consecutive_errors == 0` 且 `after.consecutive_errors > 0`
3. **错误率飙升**：`after.error_rate - before.error_rate >= 10pp`
4. **smoke test 失败**：任一关键工具调用返回异常/报错

---

## 四、显著性阈值（防噪声误判）

变化必须超过阈值才计入评分，否则视为噪声（记 0）：

| 指标 | 显著阈值 |
|:---|:---|
| 健康评分 | ≥ ±1 分 |
| 导入耗时 | ≥ ±5% 或 ±5ms |
| 平均响应时间 | ≥ ±5% |
| 错误率 | ≥ ±0.5pp |
| 测试通过数 | ≥ ±1 个 |

---

## 五、综合判定规则

综合评分 `overall_score ∈ [-1, +1]`，由各维度"变化率 × 权重"加权求和并规范化。

| 判定 | 条件 |
|:---|:---|
| 📈 `improved` | `overall_score ≥ +0.05` 且**无否决项** |
| 📉 `degraded` | 任一否决项触发，或 `overall_score ≤ -0.05` |
| ➡️ `unchanged` | `-0.05 < overall_score < +0.05` 且无否决项 |

> 说明：阈值 ±0.05（而非 ±0.03）用于过滤测量噪声，避免"虚假的净增益"。

---

## 六、四种评估方法（多样性）

一次严格评估应综合使用以下方法，而非仅靠快照对比：

### 方法 A — 前后快照对比
`EffectEvaluator.snapshot()`（before）→ 执行改动 → `snapshot()`（after）→ `evaluate()`。
采集五维指标，按第二节权重与第三节否决规则判定。

### 方法 B — 功能 Smoke Test
改动后**实际调用**核心工具（`read_file` / `knowledge.search` / `task_tracker.list` /
`self_check.check_all` / `test_runner.run_tools`），验证不报错、返回结构正常。
用于捕获"测试未覆盖但功能已坏"的改动。

### 方法 C — 历史基线对比
与最近 N 次评估的基线对比，检测**慢性退化**（单轮无感、多轮累积的劣化）。
`CycleTracker` 负责跨轮追踪，连续 3 轮下降 → 触发暂停。

### 方法 D — 审计闭环
每条进化决策必须经历：`log(决策)` → 执行 → `update(outcome, actual_effect, effect_score)`。
**禁止**留下 `pending` 状态的审计记录（除非改动确实未发生）。

### 方法 E — 行为正确性对照（补充，v2.1）
适用于**修复行为错误**类改进（如缓存不一致、逻辑 bug），这类改进的运行时五维指标
（健康/性能/测试）往往不变，但行为从"错误"变为"正确"。

判定方式：**修复前行为错误 + 修复后行为正确 = 净增益**，用可复现的行为断言验证：

1. 明确"修复前"的错误行为（可复现：如 `audit_log.stats()` 返回过期数据）；
2. 实施修复；
3. 断言"修复后"行为正确（如返回最新数据）；
4. 将行为对照结果写入审计 `actual_effect`，`effect_verdict` 记为 `improved`（正确性修复），
   并在 `effect_score` 上采用保守正向值（如 +0.3），注明"非运行时指标，而是行为正确性"。

> 说明：方法 E 是方法 A（快照对比）的补充，用于覆盖"运行时指标测不出、但行为确实修复"的场景，
> 避免把真实 bug 修复误判为 `unchanged`（从而低估进化价值）。

---

## 七、审计闭环的数据契约

每条审计记录回填时，必须包含：

| 字段 | 必填 | 说明 |
|:---|:---:|:---|
| `outcome` | ✅ | success / partial / failed / rolled_back |
| `actual_effect` | ✅ | 量化的实际效果描述（含具体数字） |
| `effect_score` | ✅ | 综合评分（-1~+1） |
| `effect_verdict` | ✅ | improved / degraded / unchanged |
| `health_after` | ⚠️ | 改动后健康分（若有测量） |

---

## 八、防"无用功"的决策规则

采纳改进前，必须通过 `evolution_strategy.check_action` 检查，且：

1. 若预估收益 < 噪声阈值（见第四节），**不做**——纯噪声改动无价值。
2. 若改进类型为 L4/L5（架构/新能力），必须**人类审批**（保守/维护模式强制）。
3. 连续 2 次 `unchanged` 的同类型改进 → 降低该类型优先级，停止重复尝试。
4. 改进导致回滚 → 记录 anti-pattern，3 次同类回滚 → 暂停该类改进。
