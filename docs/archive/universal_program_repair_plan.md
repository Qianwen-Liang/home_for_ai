# 🔧 通用自动化程序修复 — 完整实施计划

> **目标**：在 Agent 1 的 31 个工具模块中注入 100 个 bug，测量并推高自动修复率——建立一个可量化、可复现的程序修复基准。
>
> **核心假设**：规则引擎 + 工具化沙箱验证 可以在无需 LLM API 的情况下达到**显著高于 SWE-bench 基线**的自动修复率。
>
> **版本**：v1.0 — 2026-07-25

---

## 一、问题定义

### 1.1 SWE-bench 的局限

SWE-bench（2024）是目前最权威的自动化程序修复基准：

| 指标 | 当前最优 |
|:---|:---:|
| SWE-bench Lite 解决率 | ~30% |
| SWE-bench Verified 解决率 | ~40% |
| 方法 | LLM (GPT-4/Claude) + Agent 循环 |
| 需要 LLM API | ✅ 是 |
| 需要 Issue 描述 | ✅ 是（来自 GitHub） |
| 修复验证 | 运行项目测试 |

**局限**：
1. 依赖外部 LLM API —— 离线环境无法使用
2. 需要人类写的 Issue 描述 —— 现实中很多 bug 没有清晰的 Issue
3. 只在少数大型 Python 项目上测试 —— 缺乏对小型工具类模块的覆盖
4. 不区分"偶然修好"和"真正理解 bug 的修复"

### 1.2 我们的差异化

| 维度 | SWE-bench 方法 | 我们的方法 |
|:---|:---|------|
| 核心引擎 | LLM（GPT-4/Claude） | 规则引擎 + 沙箱验证 |
| 外部依赖 | LLM API | **零外部依赖** |
| Bug 来源 | 真实 GitHub Issue | **主动注入 100 个受控 bug** |
| 验证方式 | 项目原有测试 | 项目测试 + **自动生成的回归测试** |
| 修复置信度 | 无 | **三级置信度 (G/Y/R)** |
| 根因分析 | LLM 推理 | **TracebackParser 19 种分类** |
| 可复现性 | 依赖 LLM 版本 | **完全确定性的规则引擎** |

## 二、实验设计

### 2.1 Bug 注入方案

在 `tools/*.py`（31 个模块）中注入 **100 个 bug**，按类型分类：

```
Bug 类型分布（100 个总计）：

A类 — 导入错误 (12 个)
  ├── 模块名拼写错误: import utlis → import utils
  ├── 路径错误: from .foo import bar (foo 不在同级)
  └── 缺失导入: 使用未 import 的函数

B类 — 语法错误 (8 个)
  ├── 缺失冒号: if x: → if x
  ├── 括号不匹配: print(f"x={x}"  → print(f"x={x}")
  └── 缩进错误: 混用 tab 和空格

C类 — 属性/方法名错误 (15 个)
  ├── 拼写错误: .appen() → .append()
  ├── 大小写: .Title() → .title()
  └── 错误属性名: obj.length → obj.len

D类 — 类型错误 (10 个)
  ├── None 解引用
  ├── str + int 拼接
  └── 迭代非可迭代对象

E类 — 逻辑错误 (12 个)
  ├── 条件反转: if x > 0 → if x < 0
  ├── 边界错误: range(n) → range(n-1)
  └── 参数顺序错误

F类 — 返回值错误 (10 个)
  ├── 返回 None 而非预期类型
  ├── 返回错误字段名
  └── 异常被静默吞掉

G类 — 索引/键错误 (10 个)
  ├── dict[key] 不存在
  ├── list[index] 越界
  └── 默认参数可变对象陷阱

H类 — 资源/IO 错误 (8 个)
  ├── 文件未关闭
  ├── 路径拼接错误
  └── 编码未指定

I类 — 并发问题 (5 个)
  ├── 竞态条件
  └── 非线程安全操作

J类 — 性能退化 (10 个)
  ├── O(n²) 本应是 O(n)
  ├── 不必要的重复计算
  └── 内存泄漏
```

### 2.2 Bug 注入方法

```python
# 不直接修改源文件，而是创建变异副本
# research/bug_injection/bugs.json

{
  "bug_id": "B001",
  "type": "import_error",
  "file": "tools/offline_runner.py",
  "line": 15,
  "original": "import json",
  "mutated": "import jsno",
  "symptom": "ImportError: No module named 'jsno'",
  "auto_fixable": true,
  "difficulty": 1
}
```

每个 bug 注入后：
1. 运行原有测试 → 记录哪些测试失败
2. 捕获完整 traceback
3. 存储到 `bugs.json` 作为 ground truth

### 2.3 评估流程

```
注入 100 个 bug 到 tools/*.py 变异副本
        │
        ▼
┌──────────────────────────────────────────┐
│  对每个 bug:                              │
│                                           │
│  ① 运行 test_runner → 获得 traceback      │
│  ② safety_net.record_event(error, tb)     │
│  ③ safety_net.auto_trigger_repair         │
│  ④ offline.execute(修复任务)               │
│  ⑤ 验证修复:                              │
│     - 原测试是否通过？                      │
│     - 是否引入新 bug？                      │
│     - 修复是否改变了语义？                   │
│  ⑥ 记录结果                               │
└──────────────────────────────────────────┘
        │
        ▼
   统计自动修复率
```

## 三、量化指标

### 3.1 核心指标

| 指标 | 定义 | 目标 |
|:---|:---|:---:|
| **自动修复率 (AFR)** | 无需人工干预即修复的 bug 比例 | ≥ 40% |
| **修复正确率 (FCR)** | 修复后测试全部通过 + 无语义变更 | ≥ 90% |
| **平均修复时间 (ART)** | 从检测到修复完成的时间 | ≤ 30s |
| **置信度准确率** | GREEN 修复的正确率 | ≥ 95% |
| **覆盖率** | 被修复的 bug 类型 / 总类型 | ≥ 70% (7/10) |

### 3.2 对比基线

| 方法 | AFR | 备注 |
|:---|:---:|------|
| SWE-bench Lite (LLM) | ~30% | 需要 GPT-4 |
| 纯随机修复 | ~5% | 下界 |
| 纯规则引擎 (预期) | ~25% | A类+B类+C类+G类 |
| **规则引擎 + 沙箱验证 (目标)** | **≥ 40%** | 确定性 + 验证闭环 |
| 理想上限 | ~60% | E类(逻辑错误)和I类(并发)极难自动修复 |

### 3.3 按 Bug 类型的预期修复率

| 类型 | 预期 AFR | 方法 |
|:---|:---:|------|
| A类 — 导入错误 | 70% | 搜索项目文件 → 修正路径 |
| B类 — 语法错误 | 60% | AST 解析 → 补全 |
| C类 — 属性错误 | 40% | Levenshtein 距离 → 建议 |
| D类 — 类型错误 | 30% | 很难（需要理解类型语义） |
| E类 — 逻辑错误 | 5% | 极难（需要理解意图） |
| F类 — 返回值错误 | 20% | 模式匹配 |
| G类 — 索引/键错误 | 50% | 添加 .get() 或边界检查 |
| H类 — IO 错误 | 60% | 添加编码参数、with 语句 |
| I类 — 并发问题 | 0% | 当前不可自动修复 |
| J类 — 性能退化 | 20% | 识别重复计算 |

## 四、分阶段实施计划

### Phase 1：Bug 注入框架

**目标**：创建自动注入和评估框架

| ID | 任务 | 预估 |
|:---|------|:---:|
| Q1.1 | 创建 `research/bug_injection/injector.py` — 按模板注入 bug | ~200行 |
| Q1.2 | 创建 `bugs.json` — 100 个 bug 的定义（含 ground truth） | ~500行 |
| Q1.3 | 创建变异副本机制（不修改原文件） | ~100行 |
| Q1.4 | 验证：注入后运行 test_runner，确认每个 bug 有对应的测试失败 |

**预期耗时**：2 轮对话

---

### Phase 2：自动修复批量执行

**目标**：对 100 个 bug 批量运行自动修复流水线

| ID | 任务 | 预估 |
|:---|------|:---:|
| Q2.1 | 创建 `research/bug_injection/evaluator.py` — 批量评估引擎 | ~250行 |
| Q2.2 | 集成 safety_net → auto_trigger_repair → offline 全链路 | ~100行 |
| Q2.3 | 运行全部 100 个 bug 的自动修复（可分批） | 执行 |
| Q2.4 | 生成初步统计报告 | 自动 |

**预期耗时**：2-3 轮对话

---

### Phase 3：修复引擎增强

**目标**：基于 Phase 2 的结果，增强规则引擎

| ID | 任务 | 预估 |
|:---|------|:---:|
| Q3.1 | 分析 Phase 2 失败案例，识别规则引擎盲区 | ~150行 分析 |
| Q3.2 | 新增修复规则（针对失败最多的类型） | ~200行/类型 |
| Q3.3 | 添加"多修复候选 + 逐个验证"策略 | ~150行 |
| Q3.4 | 第二轮评估 → 对比改进前后的 AFR | 执行 |

**预期耗时**：2-3 轮对话

---

### Phase 4：最终报告

**目标**：生成可发表的基准测试报告

| ID | 任务 | 预估 |
|:---|------|:---:|
| Q4.1 | 生成完整统计报告（AFR/FCR/ART/覆盖率） | ~300行 |
| Q4.2 | 与 SWE-bench 的详细对比分析 | ~200行 |
| Q4.3 | 失败案例深度分析 | ~200行 |

## 五、技术架构

### 5.1 数据流

```
┌─────────────────────────────────────────────────────┐
│                 Bug 注入引擎                          │
│  bugs.json → 变异副本 → test_runner → 确认 bug       │
└─────────────────┬───────────────────────────────────┘
                  │ 100 个已验证的 bug + traceback
                  ▼
┌─────────────────────────────────────────────────────┐
│                 修复评估引擎                          │
│  ┌─────────────────────────────────────────────┐    │
│  │  对每个 bug:                                  │    │
│  │    safety_net.auto_trigger_repair             │    │
│  │    → offline.execute                          │    │
│  │    → test_runner 验证                         │    │
│  │    → 记录: [bug_id, 成功/失败, 耗时, 置信度]   │    │
│  └─────────────────────────────────────────────┘    │
└─────────────────┬───────────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────────────┐
│                 分析报告引擎                          │
│  按类型统计 AFR → 与 SWE-bench 对比 → 失败分析       │
│  → 改进建议 → 生成 paper-ready 报告                  │
└─────────────────────────────────────────────────────┘
```

## 六、预期贡献

### 6.1 如果 AFR 达到 40%+

1. **零 LLM 依赖的方法论** — 证明规则引擎 + 沙箱验证可以达到与 LLM-based 方法可比的修复率
2. **新的基准** — 为程序修复社区提供一个轻量、可复现的评估基准
3. **可量化的失败分析** — 精确知道哪些类型的 bug 是规则引擎的天花板
4. **实践指南** — "如何为你的代码库建立自动修复流水线"

### 6.2 对程序修复领域的贡献

| 贡献 | 说明 |
|:---|------|
| 确定性修复 | 规则引擎的修复 100% 可解释（vs LLM 黑盒） |
| 离线可用 | 无需 LLM API，任何环境都能运行 |
| 小型模块覆盖 | 补充 SWE-bench 只测大项目的空白 |
| 置信度框架 | GREEN/YELLOW/RED 三级，指导人工介入 |

## 七、风险与应对

| 风险 | 概率 | 应对 |
|:---|:---:|------|
| 规则引擎修复率远低于预期 | 中 | Phase 3 增强规则 + 多候选验证 |
| 某些 bug 类型的修复引入新问题 | 中 | test_runner 全量回归 + 语义差异检测 |
| 100 个 bug 执行时间过长 | 低 | 分批执行 + offline 后台模式 |
| bugs.json 定义不准确 | 低 | 先注入再验证，只保留确认触发测试失败的 bug |
| 变异副本与原文件不同步 | 低 | Git-based 分支管理 |
